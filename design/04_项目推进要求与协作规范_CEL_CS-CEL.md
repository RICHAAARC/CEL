# CEL 项目推进要求与协作规范

版本：1.2

整理与核对日期：2026-10-03  
适用项目：Communication-Equivariant Localization with Correspondence Selectivity（CEL / CS-CEL）  
用途：任务启动、方法实施、子智能体协作、独立审查、运行交付与阶段交接。

本项目研究真实通信条件下的局部语音 Deepfake 检测与时间定位。推进工作应围绕冻结的研究问题，完成真实实现、必要对照与可解释的证据交付。核心要求是：**方法优先、协议内推进、最小必要治理、单线单写者、同版独立审查、完整保留结果。**

本文规定协作与工程推进方式。方法语义、实验判据和执行条件引用 01、02、03；本文的整理不产生新的实验结果或具体执行授权。

## 2 每轮任务与完成要求

每轮先写出一条可检验的任务定义：

> 本轮在【Stage/phase 与 scope】中，针对【现象或缺口】，检验【机制假设或实现条件】，推进【实际入口与模块】，使用【必要对照与观察】判别；结果最多支持【证据范围】。

按以下顺序推进：

1. **恢复必要状态。** 确认目标文档版本、工作目录、当前阶段、已有证据和未解决问题；定向追溯原始记录。
2. **定位问题类别。** 区分方法假设、统计不足与工程错误，说明本轮能回答的具体问题。
3. **推进实际路径。** 沿运行入口核对配置、数据、调用链与输出来源，落实到 localizer、W/R、物理时间网格适配、CEL/CS 损失或训练评价 runner。
4. **完成判别验证。** 使用能回答问题的最小工程检查；涉及正式命题时，执行该阶段完整的预注册验证要求。
5. **交付判断与证据。** 说明实现变化、观察结果、可支持的结论、未核验范围及下一动作。

纯文档任务以文档准确、可用为完成目标。方法实施以实际路径和证据为完成依据。得到有效负结果、确定合法终点或排除一条不成立的解释，也属于项目进展。

## 3 阶段推进与并行边界

阶段与转换以 03 第 4、35 节为准。以下是协调工作时的索引，不替代各阶段条件。

| 阶段 | 推进重点 |
| --- | --- |
| Stage P0–P3 | 完成受控 transport、最小 localizer、oracle 对照和 U-REF 资源筛查；只形成 screen 结论 |
| Stage 0A / 0B | 核实真实参考可行性与早期采集条件，完成正式协议冻结 |
| Stage 1 | 在对应 scope 验证 F1/F2 前提 |
| Track L 与 Track C | 在 F1/F2 同 scope 支持后，推进 Localizer 与 W/R 的开发、资格验证、锁定和独立测试 |
| Stage 4D / 4P / 4L / 4T | 满足合流条件后，先开发并固定机制模型，再估计功效和样本量、完成机制锁定，最后作 F4/F5/F6 正式检验 |
| Stage 5T | 按前置条件和冻结方案评价真实通信链 |
| Stage 6D / 6L / 6T | 按前置条件推进 CS 扩展并检验 F7 |
| Stage 7 | 汇总冻结产物，形成主张与证据绑定的最终结果包 |

Track L 与 Track C 可按 03 并行推进；资源受限时可优先 W/R 这一关键可行性环节。阶段并行不等于允许跨阶段读取数据，也不等于多个实施者可以同时修改同一对象。

每轮只推进当前前置条件满足、且已在任务范围内的阶段。达到失败或不确定终点时，按03保存该版本结果，再按第39节主动完成授权内的失败诊断、文献检索、新路线选择与验证，不以移交建议代替后续工作。

## 4 方法实现与信息隔离

### 4.1 实际实现对象

实现和审查至少能追踪以下关系：

```text
成对音频与各自物理时间网格
→ 对应关系 W 与可靠性 R 的估计及独立验证
→ 固定网格适配与有效支持
→ localizer 输出及 CEL/CS 训练目标
→ 匹配对照与独立评价
→ 阶段判定、scope 和完整结果记录
```

上图是方法依赖索引；实际执行顺序按 03。W/R 与网格适配是支撑组件，其运行成功需与 CEL/CS 机制贡献分别报告。

### 4.2 按模块限定可见信息

| 对象 | 信息与梯度边界 |
| --- | --- |
| Operational W/R | 可使用成对音频及 02 允许的表示；构造时禁止读取真假标签、Y、伪造边界、检测器输出或置信度，以及检测器侧梯度 |
| 共享或独立表示 | 严格采用 02 的 C1/C2/C3 隔离方式；审查编码器的训练来源与更新路径，不能只检查当前函数的参数 |
| CS negative bank | 按 02 第 15 节构造合法、与标签和检测器输出隔离的替代对应关系；检测器梯度不得更新其构造 |
| 监督训练 | 按相应目标使用规定的监督标签和支持范围 |
| CS informative gate | W/R 与 negative bank 冻结、对应 scope 的 F3 已支持后，按 02 读取 Y 计算适用性；结果不得反向更新 W/R 或 negative bank |
| 独立评价与分层诊断 | 按阶段数据权限与冻结条件使用标签，分别报告结构性信息隔离和经验表现 |

信息边界核验覆盖数据输入、缓存、共享表示、梯度、候选选择和评价回流。W/R 的独立验证结论不得由检测器下游表现代替。

### 4.3 有效支持与缺失语义

- 直接监督按 02 的有效集合处理；真实静音与真实 bona-fide 区域仍属于监督支持，padding/batch-fill 排除。
- W 的零行表示对应关系不可用，不表示 occupancy 或 manipulation probability 为零。
- CEL/CS 有效对应支持为空时，记录该项不适用；不能将其记作零损失。
- 无合法 negative set 的 pair 可按合同参与 CEL，但不参与 CS。
- 保存未恢复、缺失、失败、排除和不适用原因；报告各指标预定义的 eligible support 与 coverage。

## 5 必要对照与机制归因

正式对照沿用 02 第 11–12 节。最小有效验证应完整覆盖当前命题的必要对照，不能通过减少关键对照降低该命题的证据要求。

| 命题 | 必要比较与解释边界 |
| --- | --- |
| F4 | M5 对 M2 strict identity/no-transport；保存 coverage 与 common-support 描述性区域分解，不单独推断精度的因果贡献 |
| F5 | M5 对 M3′ matched aligned-supervision；保持规定的 discrepancy、R、有效支持、监督、数据和训练预算可比性 |
| F6 | M5 对 M4 same-W feature control；使用规定的 canonical feature tap 与固定网格投影 |
| F7 | 同起点、同数据和追加更新预算的 CEL/CS 对照；按冻结 finite negative bank、informative gate 和 03 判据评价，主张限定于登记候选族与scope |

M3 native 是次级诊断对照，不能代替 M3′ 产生 F5 正式结论。Formal CEL 使用 02 规定的 G-A；其他拓扑及 oracle 对象按其登记用途使用。Stage P 结果用于资源筛查，不能用于事后选择有利的正式方法定义、对照或阈值。

所有量化通过条件、预算和统计参数直接引用 03 的唯一数值注册表与决策函数，不在协作模板中维护第二份参数。

## 6 数据与统计纪律

数据划分、source identity 继承、seal、lock 和解封时机按 03 第 5–8 节执行。采集、开发、资格验证、正式测试和结果分析各自使用其允许的数据。

1. **保持预注册口径。** 保存样本身份、纳入与排除依据、失败和缺失；每项指标报告实际分母、适用支持与覆盖率。
2. **满足正式要求。** 最低样本量、统计功效、精度、seed、重采样单位和多重比较规则均以 03 为准。开发检查不能替代正式统计。
3. **有限补样。** 仅按03第7.14、8.10节在正式effect/实际test CI读取前依dev规划调整样本；评价后仅作预声明、与effect无关的数据损坏/缺失替换，不能边看CI边加样。
4. **保留终局结果。** 正式效果已读取后的终局不确定，按 03 处理；预声明的数据损坏或缺失替换须遵守与 effect 无关的规则。
5. **保持 scope 一致。** 每个正式结论绑定 CTRL 或明确 REAL scope，按继承规则组合证据。

不得选择性丢弃失败 run、只保留有利 seed，或把重采样次数当作新增独立样本。结构性信息泄漏与真实性分层表现差异分别判断。

## 7 最小治理与有效验证

最小治理指只保留对当前问题和已采用协议必要的要求。01/02/03 已规定的版本身份、hash、seal、lock、统计功效、真实性审计及证据字段属于正式有效性条件，应在相应阶段落实。

| 工作类型 | 执行要求 |
| --- | --- |
| 文档与简单机械变更 | 核对内容、引用和直接受影响对象，避免启动无关运行 |
| 方法实现与接口变更 | 定向检查真实调用路径、数据与梯度边界、支持语义和必要对照 |
| 已通过检查后的继续修改 | 根据新差异、失败或未决疑点补充受影响检查，保留仍有效的证据 |
| 正式运行 | 完整执行该阶段预注册统计与审计要求；03 第 29–30 节要求的核验不能被代理意见替代 |
| 阶段与最终交付 | 核对产物身份、原始记录、判定依据、失败账本和 claim-evidence 对应关系 |

环境、资源与依赖检查服务于实际运行问题及既定交付要求。复用已跑通的安装、模型加载、缓存、资源释放和恢复路径；科学路线与候选选择仍遵循冻结顺序。

按阶段建设必要入口与记录，避免为尚未进入的阶段提前扩建无关基础设施。验证成本不能通过省略失败、不适用项或必要审查来降低。

## 8 协作角色与审查顺序

本项目使用五种协作职责，按任务阶段启用。简单读取、文档整理和边界清楚的机械修复由协调者直接处理；实质方法实施保留独立的方法审查和实现证据审查。

| 角色 | 职责与边界 |
| --- | --- |
| 实施者 | 负责同一实施线的代码修改、必要验证和范围内修复；交付可定位的版本、差异、结果及未决问题 |
| 方法审查者 | 独立检查原语与方法合同、机制必要性、正式对照、预算可比性、路线及 claim scope；只读审查 |
| 实现与证据审查者 | 独立追踪实际入口、信息与梯度流、数据划分、版本与产物身份、原始记录及判定实现；只读审查 |
| 协调与综合者 | 明确目标与任务范围，组织依赖和资源，汇总有效意见与分歧，形成可交付状态 |
| 里程碑审计者 | 在正式阶段交付、阶段收束或最终结果包形成时，独立核验关键结论与证据绑定 |

03 第 38 节的失败处理 owner 继续有效：Implementer 对应实施职责，Implementation Auditor 对应实现与证据审查；Method Architect、Research Planner、Research Scout 的具体任务分别由任务卡指定负责人，覆盖方法诊断、研究规划和必要的外部研究。协作记录使用角色全称，与 03 的 A1–A25 审计检查编号区分。

执行顺序如下：

1. 协调者明确当前目标、stage/phase、scope、修改范围、交付物和必要停止条件。
2. 实施者完成可审查版本，提供最少但足以定位的代码与证据入口。
3. 方法审查者与实现证据审查者并行、独立检查同一版本；各自直接读取源码和证据，不以实施总结或另一审查者意见代替判断。
4. 审查期间保持对象稳定。若发生修改，标明新版本并复核受影响结论，确保交付意见共同覆盖最终版本。
5. 实施者连续完成已有授权内的修复。协调者汇总当前有效意见，明确未解决问题及其影响。
6. 到达相应里程碑后进行独立审计，并按协议交付科学判定与需要用户决定的研究事项。

同一实施线保持唯一代码写者。确需并行实施时，任务卡划定互不重叠的写入范围、共享接口与集成责任人；最终集成版本重新核对受影响关系。独立审查者不参与被审变更的实现；自查按自查报告。

并发不足时分波次执行。角色不要求同时在线；审查对象准备就绪后再启动审查。无法完成某项独立审查时，如实报告缺口。

## 9 模型选择与上下文成本

协调会话沿用用户配置。子任务按复杂度、错误代价、独立判断需要和工具实际支持的配置选择模型与推理强度。

| 任务类型 | 配置原则 |
| --- | --- |
| 路径、字段、日志、文档与机械核对 | 优先直接处理；有明确并行收益时才委派 |
| 边界清楚的实现与定向验证 | 使用能准确理解相关接口与代码的配置 |
| 跨模块执行、资源或梯度问题 | 给予足够推理预算与关键调用链上下文 |
| 数学合同、信息隔离、统计与科学主张 | 保留充分推理与必要独立复核 |
| 关键里程碑审计 | 按影响范围配置审查深度，重点核验原始证据和结论边界 |

每次委派简记任务类型、实际模型/强度和选择理由。传递紧凑任务卡及必要证据路径，避免复制与任务无关的完整历史；关键边界不能因压缩遗漏。

## 10 失败分类与继续条件

失败类型及终点以 03 第 37–39 节为准。

| 情形 | 处理要求 |
| --- | --- |
| 工程或实现真实性问题 | 记录具体错误与影响，按协议标记受影响结果失效；在授权内修复，从受污染阶段之前恢复或重跑，并保留原记录 |
| 科学失败或 practical null | 保存冻结verdict和claim边界；按03第39节主动检索文献、查重、选择新路线并推进授权内新版本实现与验证 |
| 统计不足或终局不确定 | 仅使用协议允许的 reserve 与精度流程；资源上限或终点到达后保留不确定结论 |

工程修复不得改变算法语义、阈值、路线顺序或正式对照。开发和资格验证阶段只执行协议允许的候选转换；W/R 在正式 Corr-Test 解封后不得于同一证据版本中换路线。

某个 locked realization 失败与整个预注册 operational family 被否定分别报告。新的研究假设按03第39.4–39.7节进入新版本评估，原版本的测试使用记录和结果继续保留。

### 10.1 失败后持续研究与防重复

按03第39节维护跨版本append-only失败账本、可读route fingerprint、精确run身份和数据暴露记录。每次实施前检索既有失败；已在相同适用条件下失败的机制，不因改名、换seed或换版本再次消耗预算。合法再试必须指向具体旧记录和可检验的新依据。

失败诊断后由负责人自行检索原论文、作者实现与官方资料，核实适用前提及反证，形成有限候选和最小判别实验，再在授权范围内实施。所有候选取舍、失败、不确定、无效run及累计资源消耗均保留；文献相关性不能代替实验证据。记录结构、预算和停止条件只在03维护，不复制第二套规则。

## 11 授权范围与连续推进

用户的当前目标、修正及仍适用的授权决定可以执行的动作。当前用户已要求失败后自主检索文献、制定新路线并继续研究；这覆盖保持01原语、遵守证据隔离且在已有资源/数据/执行授权内的版本迭代，不需要逐条新路线再次确认。协调或审计角色核对具体范围，不扩大付费、外部写入或受限数据权限。

- 对已授权的实现、定向验证、工程修复和交付持续推进；普通范围内实现选择自行处理，必要取舍在交付中说明。
- 方法定义、评价口径、预算、数据范围和路线的变化，先核对任务是否已包含；超出范围时提交具体证据、拟议动作与待决定项。
- 真实模型/GPU/Colab 运行、数据解封和外部写入，须有覆盖当前动作与范围的授权；已有适用授权不重复询问。
- 分支、提交、推送、合并、删除及跨路线集成按任务授权和工具边界处理，不因进入下一步骤就自动新增审批。
- 向其他用户聊天派发或发送结果，遵循已有明确协作安排及平台要求；任务内子智能体按本轮授权范围工作。

需要用户决定时，先完成可独立推进的已授权工作，再说明事实、证据、具体方案及超出范围的部分。工具拒绝或执行能力不足时，报告实际限制与已完成内容。

科学 verdict 按冻结判据和完整证据产生；用户确定研究目标、授权边界及超范围投入；负责人自主选择和实施授权内候选。研究决定与当前证据能支持的科学结论分别记录。

## 12 Notebook 与真实运行交付

Notebook 按 03 第 31–33 节保持薄 orchestration。每个 stage/phase 使用唯一入口，Run all 只执行本次选定且满足前置条件的阶段任务。

本地脚本与Notebook均按03第32–33节完成源码版本定位、01/02/03 hash核验、当前阶段适用的lock/seal与数据manifest核验、环境准备及冻结缓存加载，然后调用实际runner并保存checkpoint、raw records、manifest及资源记录。仅Colab使用Drive时挂载；Stage P及开发阶段不要求未来阶段才生成的锁，正式test仍须具备全部对应证据。本地环境与启动实例分别引用03第32、7.19节，不在本文复制另一份配置。

- 同一入口不同时读取本应由 seal 隔离的数据划分。
- 算法与科学配置保存在项目规定的实现与配置位置，Notebook 不维护第二份算法或临时改阈值。
- 完全冻结backbone的阶段按03第32.1节的完整cache key校验：source身份、实际波形及变换/预处理、模型revision、特征层与精度。不能仅凭同一source identity复用原音与不同通信realization的特征。
- 中断续跑使用同一 run manifest 及完整 optimizer/scheduler state；无法恢复时按 03 重启并保留原失败记录。
- OOM 等资源问题定位到实际阶段、计算图和活张量，修复后仍保持方法语义及正式预算。
- Notebook 交付与真实执行分别报告。用户要求自行运行时，完成必要检查和交付，实际运行状态等待运行证据更新。

## 13 证据等级与交付口径

证据始终绑定代码与协议版本、阶段、数据身份和 scope。结论以 02 第 20 节、03 第 36–37 节为准。

| 证据 | 可支持的范围 |
| --- | --- |
| 工程检查（运行设备不限） | 实际覆盖的接口、接线、支持语义及实现性质；不自动形成科学阶段判定 |
| Stage P 与 oracle screen | 资源筛查及声明构造下的候选信号；不产生 F1–F7 正式结论 |
| 独立前提与可行性验证 | 对应 scope 的 F1/F2/F3 及 localizer 判定，是否允许进入机制验证依 03 |
| 正式机制检验 | 同 scope 的 F4/F5/F6 全部支持后，形成该范围内的 CEL 机制贡献 |
| 真实链与扩展证据 | Strong Real CEL 需要同一 REAL scope 的 F1–F6 与 Stage 5；CS 附加主张按 F7 及前置条件判定 |
| 代理审查和工程交付 | 表示实际覆盖范围内的审查或交付状态，实验与科学结论另附证据 |

正式证据等级由协议、数据身份、阶段和scope决定，不由CPU/GPU或本地/Colab决定。满足完整协议的受控实验可形成CTRL范围内的正式证据；GPU上的合成安装检查仍只是工程验收。

结果包保留全部正式 run、资格验证历史、invalidation、失败、缺失、排除与终局证据。不得跨 scope、跨方法版本或跨分支挑选最佳结果拼接完整方法主张。

Stage 7 从冻结产物生成结果包，按 03 保存判定表、scope、锁定信息、对照核验、归因分解、失败账本及 claim-evidence matrix。

进度更新聚焦新发现、实际变化、验证结果和未决事项。正文给出结论与可定位入口，完整日志保存在产物中。
